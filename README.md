# Atlas — Agentic RAG Multi-Tool Assistant (MCP)

This is the complete source project updated to use the Model Context Protocol (MCP).
The previous React UI has been replaced with the updated Atlas light UI.

## Architecture

```text
User
  ↓
React / Vite
  ↓
FastAPI
  ↓
Custom Agent + MCP Client Manager
  ↓
 ┌───────────────────────────────┐
 │ MCP Servers (stdio)           │
 │                               │
 │ RAG MCP Server                │
 │   └─ search_documentation     │
 │                               │
 │ Python Code MCP Server        │
 │   └─ execute_python_code      │
 │                               │
 │ Calculator MCP Server         │
 │   └─ calculate_expression     │
 └───────────────────────────────┘
  ↓
ChromaDB / local Python sandbox / calculator
```

The Agent Core does not directly execute the RAG, Python, or calculator implementations.
It discovers MCP tools with `list_tools()` and invokes them with `call_tool()`.

## MCP acceptance checks

- `agent.py` contains no direct RAG/Python/calculator execution implementations.
- Tool implementations are isolated under `backend/servers/`.
- MCP tools are discovered through `list_tools()`.
- Tool execution uses MCP `call_tool()`.

## MongoDB Authentication, RBAC, and Prompt Management

The backend now stores accounts in `users`, role definitions in `roles`, role grants in `permissions`, and editable prompt records in `prompts` in MongoDB. The initial roles are `admin` and `user`; role documents are referenced by `role_id` and `role_code`, not duplicated as role names. Only administrators may call `/api/prompts` CRUD endpoints. Authenticated users can use the RAG chat API but receive `403 Forbidden` for prompt management.

1. Copy `backend/.env.example` to `backend/.env` (preserve your existing settings). Set `MONGODB_URL`, `MONGODB_DB`, a random `AUTH_SECRET_KEY` of at least 32 characters, `ADMIN_USERNAME`, and a strong `ADMIN_PASSWORD`. Do not commit `.env`.
2. Install backend requirements: `pip install -r requirements.txt`.
3. Ensure MongoDB and Ollama/MCP services required by your existing project are running, then start FastAPI using your existing run command. Startup creates the collections/indexes, seeds the two roles, role permissions, and initial prompt documents without overwriting existing prompt edits.
4. The first configured admin account is created from `.env` only when the username does not already exist. Changing `ADMIN_PASSWORD` later does not reset an existing account.
5. Start the frontend with `npm install` and `npm run dev`. Sign in with the configured admin account; create normal users in MongoDB by assigning the `user` role's `_id` to their `role_id` and storing a PBKDF2 password hash, or ask for a registration endpoint if you want self-service user creation.

Prompt endpoints: `GET /api/prompts`, `GET /api/prompts/{id}`, `POST /api/prompts`, `PUT /api/prompts/{id}`, `DELETE /api/prompts/{id}`. All require a bearer token and enforce admin-only access on the server. Prompt values are read from MongoDB at each model call.


## MongoDB roles and prompt management

The backend uses the `users`, `roles`, `permissions`, and `prompts` collections in MongoDB. Initial prompt definitions live in `backend/prompts_seed.json`, not in `app/agent.py`. Run `python seed_prompts.py` from the `backend` directory to seed any missing prompt records; `$setOnInsert` preserves prompts already edited in the admin UI. The app also checks the seed file during startup.

Set a unique random `AUTH_SECRET_KEY` in `backend/.env` before starting the backend. Do not reuse a secret that has been shared in chat or committed to source control. Existing admin passwords are not overwritten from `.env` on startup. If an admin user already exists, continue using its current password or update it through a deliberate password-reset process.

Prompt-management endpoints require a valid bearer token and a role permission grant. Users without prompt permissions receive HTTP 403 from `/api/prompts`, including direct API requests.


## Audit logging and error logging

The API writes structured logs to MongoDB using the database configured by `MONGODB_URL` and `MONGODB_DB`.

- `log_master`: audit event registry, seeded non-destructively with `$setOnInsert`.
- `audit_logs`: append-only audit records for successful sign-in, user creation, and prompt create/update/delete actions.
- `error_master`: error-code registry, seeded non-destructively with `$setOnInsert`.
- `error_logs`: structured error occurrences with severity, actor when known, request method/path/IP, trace ID, source, UTC timestamp, and stack details for unexpected exceptions.

The log indexes and initial registry rows are created at application startup. Log writes are best-effort and must not interrupt the primary operation. Credentials, bearer tokens, full request headers, request bodies, prompt contents, and document contents are not written to logs. The Error Logs UI omits stack traces.

### Admin log endpoints

All endpoints below require a valid bearer token and the existing admin permission grant (`prompts.read`).

- `GET /api/admin/audit-logs?limit=50&offset=0`
- `GET /api/admin/audit-logs?event_code=LOG.ATLAS.USER.LOGIN`
- `GET /api/admin/audit-logs?username=admin`
- `GET /api/admin/audit-logs?entity_id=<entity-id>`
- `GET /api/admin/error-logs?limit=50&offset=0`
- `GET /api/admin/error-logs?error_code=ERR.ATLAS.API.CHAT.ANSWER_FAILED`
- `GET /api/admin/error-logs?severity=HIGH`
- `GET /api/admin/audit-logs/events`
- `GET /api/admin/error-logs/registry`

Pagination is capped at 200 records per request. Audit log endpoints are read-only: the application intentionally exposes no edit or delete API for audit records.
